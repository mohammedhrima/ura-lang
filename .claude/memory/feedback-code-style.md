Study the code style used in src/ir.c and src/main.c and respect it.

**Why:** user wants changes that read like their own code.
**How to apply:** match naming (`ucg_*` records a node, `llvm_*` emits it, cases in `ucg_compile`), `// clang-format off/on` around nested calls, existing indentation. ucg is an abstraction over LLVM so other backends can be swapped in later: LLVM API calls go only in `llvm_*` functions; `ucg_*` and `ucg_compile` cases call `llvm_*` wrappers, never `LLVMBuild...` directly. Errors go through one function only, `add_error(s, e, msg, help)`, called only from check_* functions in check.c (plus `expect` there for the parser's "consume or report"). ura-lang's main point is readable syntax: never propose symbol-heavy syntax for the language (user rejected `out << x << "\n"`); prefer plain calls like `fmt.out("hp: ", hp, "\n")`. New code copies the exact shape of the code next to it (same braces `{}` on if/else, same layout): user had to fix a FLOAT case that dropped the braces its INT neighbor had. Function names must be readable and follow the family already in use (codegen_proto, codegen_structs, codegen_statements, codegen_in_variable; ucg_get_param/ucg_get_attr; find_function/find_struct/find_method): user rejected `codegen_place`, `distance`, `is_ref`/`is_bind`, `FOLLOW`/`TARGET` for being unclear. Don't add comments to code (user rejected `// break: expect 3` style test comments). Readability is crucial: give a field a name that says what it holds (add e.g. `Node *to_call` to the union) instead of reusing `left`/`right`; name lookups by what they find (`find_function`, not `find_variable` for functions). The user's own renames show the style to copy (2026-11-18): macro_is_true -> macro_cond, find_module -> find_package, parse_module -> parse_package, instantiate -> init_from_template, macro_text -> macro_to_text; `use` loads packages, not modules. Prefer short plain words the user already uses (find_, parse_, init_, check_, _cond, _to_) over invented abstractions; when unsure, ask for the name instead of making one up. Never add a new field to Token, Node or another struct without asking first: the codebase stores per-node data in the existing left/right unions of Node; propose where data goes and wait for the user (user rejected an `operator_type` Token field, 2026-11-18). In loops, use early `continue` guards (`if (!includes(...)) continue; if (!strcmp2(...)) continue; return child;`), not one combined `&&` condition. A condition that doesn't fit one line is split into named bools first (`bool is_x = ...; bool has_y = ...; if (is_x && has_y)`), never a multi-line `&&`/`||` or a wrapped ternary; applies to the whole codebase. Long calls that don't fit one line go Flutter-style: break after `(`, one argument per line, `)` on its own line (.clang-format: AlignAfterOpenBracket BlockIndent, BinPackArguments/Parameters false; format with ~/.local/opt/llvm-15/bin/clang-format, llvm-12's is too old). ColumnLimit is 87. Every `add_error(` call puts each of its 4 arguments on its own line, even short ones (user, 2026-11-19). No comments above functions (the user deleted the ones I added). A keyword is a Type enum value (in ucg.c and type_names) plus an entry in the keywords table, never `strcmp2(token->name, "from")` (user, 2026-11-19). Prefer plain data tables over machinery: builtins became a second `Keyword builtins[]` table (same row shape as keywords: name + Token template) looked up by `find_builtin`, which the user called "beautiful readable code"; they rejected a `Builtin` struct with function pointers and flags (takes_one, raw_args...) as over-engineered, and asked for real types inline instead of wrapper functions like `i32_type()` (2026-11-19). Named types follow the file's convention: `typedef struct X X;` with the other forward typedefs at the top, `struct X {...}` next to the other struct definitions, never an inline `typedef struct {...} X;` (user fixed mine). Errors: all add_error calls live in check.c (see [[feedback-errors-portable]]); prefer computing msg/help and making one add_error call over chains of add_error calls. See [[feedback-reuse]].
